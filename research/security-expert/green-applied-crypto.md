# Matt Green — distilled

> **"A Few Thoughts on Cryptographic Engineering"** blog (cryptographyengineering.com, 2011–present); Johns Hopkins University cryptography research; public commentary on deployed cryptographic systems. Green is neither a framework author nor a catalogue; he is the working-cryptographer voice that translates academic cryptography into production-engineering guidance. His blog is the clearest available source on the question AI-coding systems get wrong most often: *what cryptographic primitives should we actually use, and why is the "obvious" choice frequently wrong?*

## Why it matters for AI-coding

AI-generated crypto code is plausible and frequently wrong. Not obviously wrong — the generated code compiles, uses real API names, and looks like security. But cryptographic mistakes are subtle: using ECB mode instead of GCM, constructing an HMAC with SHA-1, implementing custom key derivation instead of HKDF, choosing RSA-PKCS1v1.5 instead of RSA-OAEP. These mistakes are invisible to a non-cryptographer reviewer, they produce no runtime errors, and they are genuinely dangerous. Green writes in the tradition of applied cryptographers who take production systems seriously — not "here is the theoretical attack on this primitive" but "here is why the construction you're using is wrong, what the right one is, and how to use it."

The `security-review` finding A02:2021 (Cryptographic Failures) is one of the hardest categories to evaluate without cryptographic knowledge. Green's blog is the practical reference for reviewers who need to know whether "this is using AES correctly" or "this HMAC construction is actually a MAC oracle."

## Key concepts the role pulls from

- **"Don't roll your own crypto" — and why the obvious safe alternative is still wrong.** Green's most-cited contribution to applied engineering: the problem with cryptographic code is not just that developers implement primitives incorrectly, but that developers assemble correct primitives incorrectly. Using AES-CBC with a random IV, HMAC-SHA256 for authentication, and RSA-2048 for key exchange — all individually correct — can still produce a broken system if the composition is wrong (e.g., MAC-then-encrypt instead of encrypt-then-MAC). The guidance is not just "use a library"; it is "use a high-level library with a safe API" (NaCl/libsodium, AES-GCM, TLS 1.3). Powers the `security-review` crypto-specific investigation.
- **Authenticated encryption as the default.** Green's consistent recommendation: use AES-GCM (or ChaCha20-Poly1305) for symmetric encryption. Not AES-CBC, not AES-ECB, not "encrypt then manually add a MAC" — AES-GCM, which provides both confidentiality and integrity in one primitive. AI-generated code frequently uses AES-CBC or even ECB. Any `security-review` that finds CBC-mode encryption without explicit MAC should cite this as an A02 finding, because the authenticated-encryption default exists precisely because MAC-then-encrypt constructions have been broken in production systems (BEAST, POODLE, Lucky Thirteen).
- **TLS is the transport layer; don't rebuild it.** A recurring Green theme: engineers who roll their own transport encryption — even using correct primitives — miss the dozens of design decisions TLS incorporates (downgrade prevention, cipher negotiation, forward secrecy). The correct choice is TLS 1.3 with a maintained library (OpenSSL, BoringSSL, rustls); the wrong choice is "I'll use AES and some HMACs over this TCP socket." The `security-review` check for A02 includes: is any non-TLS encrypted channel present? If yes, treat as a candidate finding until proven otherwise.
- **Password hashing is not the same as data hashing.** Green regularly addresses the distinction: SHA-256 is a fast cryptographic hash; Argon2id / bcrypt / scrypt are slow adaptive password-hashing functions. Using SHA-256 to hash passwords is a critical finding (A07 + CWE-916) because fast hashes are enumerable at GPU speed. The correct password-hashing algorithm in 2025 is Argon2id (NIST SP 800-132 recommends it; Green explains why). This is the finding Hunt's HIBP data surfaces in breach analysis and Green's writing explains mechanistically.
- **Randomness and key generation.** Green writes extensively on the requirement that cryptographic keys and nonces be generated by a cryptographically secure random number generator (CSPRNG), not a general-purpose random number generator. AI-generated code frequently uses `Math.random()` / `random.random()` / `rand()` for nonces or tokens. Any such usage is an A02 finding; the fix is `crypto/rand` (Go), `secrets` (Python), `crypto.getRandomValues` (Web). The distinction is invisible to a linter but critical for cryptographic security.
- **Deprecated algorithms and migration timelines.** Green tracks the deprecated-algorithm landscape: SHA-1 is broken for collision resistance (since 2017); MD5 is broken for signatures; RSA-PKCS1v1.5 is vulnerable to Bleichenbacher attacks; 3DES has a birthday-bound weakness at large-volume deployments. The `security-review` dependency-scan step and A02 walk include checking for these; Green's blog is the clearest explanation of *why* each deprecated primitive is deprecated, which is necessary to make the finding convincing to a developer who has been using SHA-1 for years without visible harm.

## What to actually read (1-hour budget)

- **cryptographyengineering.com** — start with "Why I Hate CBC-Mode Encryption," "How Does Apple Pay Work?", and "A Gentle Introduction to Algorithm Agility." These three cover the load-bearing applied-crypto positions. (~30 min)
- **"Why I Write About Crypto"** — Green's framing of the gap between academic and applied cryptography. Sets up the voice. (~10 min)
- **NIST SP 800-132** (password-based key derivation) sections 4-5 and **SP 800-131A** (transitions in algorithm use) overview — the normative grounding for Green's password-hashing and algorithm-deprecation positions. (~20 min)

## What to skip

- Green's academic papers and lecture notes — valuable for cryptography research but not load-bearing for the security-review and pre-launch-audit skills. Save for deep dives on specific protocol questions.
- Blog posts on zero-knowledge proofs and advanced cryptographic protocols — relevant to specialist systems but not the day-to-day applied-engineering concerns the role addresses.

## How this anchors role skills

- [`security-review`](../../roles/security-expert/skills/security-review/SKILL.md) — the A02 (Cryptographic Failures) investigation: authenticated encryption requirement, password-hash algorithm check, CSPRNG requirement for nonces and tokens, TLS-not-hand-rolled requirement, deprecated-algorithm scan. Green is the working-cryptographer citation for each of these.
- [`pre-launch-security-audit`](../../roles/security-expert/skills/pre-launch-security-audit/SKILL.md) — the crypto surface check at launch: keys generated correctly? Stored correctly? Algorithms current? Any hand-rolled crypto present? Each question maps to a Green-blog-backed position.
- [`threat-model`](../../roles/security-expert/skills/threat-model/SKILL.md) — cryptographic controls for STRIDE's "Tampering" and "Information Disclosure" categories need to be evaluated for correctness, not just presence. "Uses AES" is not a control; "Uses AES-GCM with a 96-bit random nonce and a unique key per session" is.
- [`llm-risk-assessment`](../../roles/security-expert/skills/llm-risk-assessment/SKILL.md) — LLM-generated code for encryption is a high-risk surface; the assessment should flag any AI-generated crypto code for explicit review against Green's applied-crypto positions before shipping.

## Cross-role connection

Green's working-cryptographer voice is the security-specific parallel to the engineer role's "use the library, not the primitives" discipline. Both argue the same position from different angles: the engineer role cites abstraction as a complexity-management tool; Green cites the failure modes of hand-assembled primitives as the reason to prefer high-level APIs. When a software engineer writes `nacl.secretbox(plaintext, nonce, key)` instead of assembling AES-CBC + HMAC, they are applying both the engineer's abstraction principle and Green's applied-crypto recommendation simultaneously. The two roles reinforce each other on this point.
