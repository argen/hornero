# Google BeyondCorp — distilled

> **"BeyondCorp: A New Approach to Enterprise Security"** (Ward & Beyer, Google; USENIX ;login:, 2014); **"BeyondCorp: Design to Deployment at Google"** (2016); **"BeyondCorp: The Access Proxy"** (2017); **"BeyondCorp: Migrating to a Model of Zero Trust"** (2018); subsequent Google implementation papers (2019-2021). BeyondCorp is not a book — it is a body of engineering papers documenting Google's decade-long migration away from perimeter-based network security. The model it describes — zero trust, device-identity, user-identity, and context-aware access replacing VPN-plus-firewall — is now the operational reference for enterprise security architecture and increasingly for product-level identity design.

## Why it matters for AI-coding

AI-era identity models default to perimeter-based thinking. Generated auth code verifies that a request comes through the right endpoint, passes a valid token, and proceeds — without asking whether the device is managed, whether the user's context is normal, or whether the network position of the request carries any meaningful trust signal. This is the perimeter model: trust the request if it came from inside the fence. BeyondCorp's argument, validated by Google's decade-long deployment and the industry's subsequent adoption (Cloudflare Access, Okta, AWS IAM, Azure Zero Trust Framework), is that the perimeter no longer exists as a meaningful security boundary — every request must be evaluated on identity and context, regardless of network origin.

For AI-coding teams, the practical consequence is architectural: every generated auth design should be evaluated against zero-trust principles. Does this grant access based on network position? If yes, that's a design-time risk for systems where the network perimeter is not reliably controlled.

## Key concepts the role pulls from

- **Network as untrusted.** BeyondCorp's foundational premise: the internal network is not a trust boundary. An attacker who gains access to the internal network — via phishing, VPN credential theft, insider threat, or cloud-misconfiguration — should not gain implicit trust to internal services. Every service must authenticate and authorise every request as if it originated from the open internet. This is the direct counter to any auth design that uses "is this request from an internal IP?" as an authorization signal.
- **User identity + device identity + context = access decision.** BeyondCorp replaces VPN-based network trust with a three-factor access model: verified user identity (strong auth, managed credential), verified device identity (device certificate, device trust level from an inventory system), and request context (time, location, risk signals). The intersection of these three, evaluated per-request, determines whether access is granted. For `threat-model` adversary calibration: a BeyondCorp system requires the attacker to compromise all three to gain access, not just steal a password.
- **The Access Proxy as the enforcement point.** BeyondCorp's implementation routes all access through a proxy that enforces the access-decision before the request reaches the backend service. Backend services are not reachable without going through the proxy. This is the operational mechanism that makes "no implicit network trust" achievable: the proxy enforces context-aware policy; backends don't need to re-implement it. For systems designing auth architecture, this pattern (centralised enforcement proxy) is the BeyondCorp recommendation over per-service auth logic.
- **Device inventory as a security asset.** BeyondCorp's device trust depends on a maintained device inventory that assigns trust levels to managed devices. An unregistered device gets low-trust access (or no access); a registered, compliant device gets higher-trust access. For enterprise product teams, this makes device management a security prerequisite — not just an IT concern. The `pre-launch-security-audit` for enterprise products should ask: is there a device-trust model? Is it enforced at the access layer?
- **Context-aware access policies.** BeyondCorp papers describe access policies that incorporate context signals: time of day, geographic location, whether the device has been recently patched, whether the user's behaviour is anomalous relative to baseline. These are the "zero-trust" policies that NIST SP 800-207 (Zero Trust Architecture, 2020) later formalised. For threat modeling, context-aware policies are controls that raise the adversary's cost: a stolen credential used from an unusual location at an unusual time triggers additional authentication or blocks access entirely.
- **Continuous verification, not session-level trust.** Traditional auth establishes a session and trusts it for the session lifetime. BeyondCorp's model re-evaluates trust continuously — a session is not a permanent grant; it is a current state. If the device's trust level drops mid-session (patch falls out of compliance; location changes unexpectedly), access is revoked or stepped up. For `security-review`, this is the design principle behind short-lived tokens and frequent re-authentication requirements.

## What to actually read (1-hour budget)

- **"BeyondCorp: A New Approach to Enterprise Security"** (2014) — the original paper. Short; the foundational argument in twelve pages. Available free via USENIX. (~20 min)
- **"BeyondCorp: Design to Deployment at Google"** (2016) — the implementation details. The Access Proxy section and the device-inventory section are load-bearing. (~20 min)
- **NIST SP 800-207: Zero Trust Architecture** (2020) — the NIST formalisation of the BeyondCorp model. Sections 2-4 are the practical reference; they define zero-trust in auditor-legible terms. (~20 min)

## What to skip

- The 2018-2021 BeyondCorp papers on migration tooling and specific Google-internal implementation details — useful for large-scale migration projects; not load-bearing for the role's skills. Skim if planning an enterprise-wide zero-trust migration.
- Vendor zero-trust marketing content (Cloudflare, Zscaler, Palo Alto BeyondCorp-branded products) — the papers are the reference; vendor documentation is useful for implementation but not for methodology.

## How this anchors role skills

- [`security-review`](../../roles/security-expert/skills/security-review/SKILL.md) — A01 (Broken Access Control) and A07 (Authentication Failures) findings that involve network-position trust or long-lived session grants cite BeyondCorp as the architectural alternative. "This grants admin access to any request from 10.0.0.0/8" is a finding; BeyondCorp is the frame for why network position is not an authorization claim.
- [`threat-model`](../../roles/security-expert/skills/threat-model/SKILL.md) — the Trust Boundaries section of the DFD is directly shaped by BeyondCorp: network boundaries that don't enforce user+device+context auth are *not* trust boundaries; they are lines on a diagram. The threat model must evaluate whether the boundary is enforced by auth or only by network topology.
- [`pre-launch-security-audit`](../../roles/security-expert/skills/pre-launch-security-audit/SKILL.md) — enterprise-facing products should be evaluated against zero-trust principles at launch: does the product support context-aware access? Are admin interfaces protected by something stronger than network perimeter? Is there a device-trust model?
- [`llm-risk-assessment`](../../roles/security-expert/skills/llm-risk-assessment/SKILL.md) — LLM06 (Excessive Agency) and LLM10 (Unbounded Consumption) are mitigated by context-aware access policies that limit what the LLM can do based on the user's verified trust level. BeyondCorp's policy model applied to agent capability scoping is a direct connection.

## Cross-role connection

BeyondCorp's zero-trust identity model affects every authentication and authorisation design decision an engineering team makes. When the software engineer role designs an auth system, the BeyondCorp patterns — user+device+context, short-lived tokens, centralised enforcement, no implicit network trust — are the architectural primitives. The security role and engineer role share BeyondCorp as a common reference, which is what makes cross-role discussion of auth architecture tractable: both roles can point to the same papers when evaluating whether a design decision trades off correctly.
